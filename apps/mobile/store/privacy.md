# What the TaskBeavo app collects

The single source of truth for the App Store privacy label (App Store Connect → App Privacy) and the Google Play data safety form (Play Console → Policy → App content → Data safety). Both forms must match this file. When a change collects a new data type, adds an SDK or changes a purpose, update this file in the same PR and add "Update App Store privacy label and Play data safety form" to the PR description (see the `mobile-platform` skill, §5). `expo-release` checks it before every production submit.

No data is used for tracking across other companies' apps or websites, so there is no App Tracking Transparency prompt. No data is sold. All data is encrypted in transit (HTTPS/TLS).

## How photos are handled

- A task photo is re-encoded on the server without metadata before anyone else sees it, so its location and camera details are never shown.
- An evidence photo's original stays in private storage, readable only through 5-minute presigned links the API gives its owner (and later the people on that booking). Its EXIF time and position are kept server-side and never exposed through the API.
- Retention: unclaimed uploads 48 hours; task photos until the task closes plus 30 days; evidence 180 days after the booking closes (18 months after payment for no-access call-outs, partial releases and refunds); anything under a dispute or claim until resolved plus 5 years (`backend/uploads/models.py`).
- Photos are deleted with the account (GDPR erasure); account deletion must be refused while a dispute is open (`gdpr-data-request`), because the legal hold doesn't survive it.

## How sign-in location and the device token are handled

- The location is city and country only ("Munich, Germany"), derived on the server from the sign-in's IP address; the address is used for the lookup and not stored. It appears only in the account owner's "New login" email.
- The device token is random and identifies nothing outside TaskBeavo; its only use is recognising known devices for the "New login" email. "Log out of all devices" (in the app or from the email) forgets every device of the account.
- Lifetime: 6 months from the last sign-in that used it, renewed at each sign-in; the API treats an older token as unknown and issues a new one (`DEVICE_TOKEN_MAX_AGE_DAYS`). On the web it is the cookie `tb_device` (httpOnly, `Max-Age` 6 months), a strictly necessary security cookie (decision 2026-11-04, ePrivacy Art. 5(3) exemption, WP194 "user-centric security"), so it needs no consent; list it in the cookie policy when `/cookies` exists.
- Both are deleted with the account (sessions are deleted with the user).
- Retention: a session record, with its location and device hash, is deleted 6 months after the session ends (logged out, revoked or expired), following the CNIL logging recommendation (Délibération 2021-122); decision 2026-11-04 (`backend/accounts/tasks.py` `purge_ended_sessions`). Live sessions are kept while in use.

## Identifiers held by SDKs (BEAV-190)

Listed in full, with lifetimes, in `docs/storage-inventory.md`. Check with the lawyer (BEAV-39) whether the forms must declare them as "Device or other IDs":

- `EAS-Client-ID`: expo-updates creates a random ID once per install and sends it to Expo on each update check, to deliver over-the-air updates. Not linked to the account.
- Stripe's SDK keeps fraud-prevention data and its `m` cookie, only from the moment a checkout screen opens.
- Sentry: JavaScript events carry no user and no device identifier; native crash reports may still carry the iOS vendor hash (`device_app_hash`) until that is stripped natively.
