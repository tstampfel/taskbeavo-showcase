# Cloudflare R2: photo and file storage

Clients upload photos straight to R2 with presigned PUT URLs; the API only issues URLs and stores keys (`backend/uploads/`). Nothing here is created automatically. Set it up per environment (staging, production) before the first deploy, then fill the variables in `docs/deploy-render.md`.

## Buckets

Create both with **EU jurisdiction** (GDPR). The API's default endpoint is `https://<account id>.eu.r2.cloudflarestorage.com`; set `R2_ENDPOINT_URL` only for another jurisdiction.

| Bucket | Variable | Access | Holds |
|---|---|---|---|
| `taskbeavo-private-<env>` | `R2_PRIVATE_BUCKET` | No public access, no r2.dev URL | Upload originals while they're checked, task photos' clean copies until a task claims them, evidence photos (original with its GPS and time, plus a clean copy), later fiscal receipt PDFs and data exports. Read only through presigned GET URLs valid 5 minutes |
| `taskbeavo-public-<env>` | `R2_PUBLIC_BUCKET`, `R2_PUBLIC_BASE_URL` | Public through a custom domain, e.g. `photos.taskbeavo.com` (`photos-staging.` on staging) | Only task photos the API re-encoded without any metadata **and a task has claimed**, at `photos/<upload id>.<ext>` |

Key layout in the private bucket: the presigned PUT lands at `users/<user id>/<task-photos|evidence>/<upload id>/upload`. `completeUpload` records the object's ETag, and processing reads only that object (`If-Match`): a file PUT again after `completeUpload` is rejected (`UPLOAD_CHANGED`) and deleted. Processing then deletes the upload key, and deletes it again after its URL expires, so nothing PUT later is kept. Every photo's clean copy is kept at `.../display.<ext>`, and an evidence photo's checked bytes at `.../original.<ext>` (with their SHA-256 on the row); no client is ever given a PUT URL for those keys. Keys hold IDs only.

Deleting an upload row (sweep, `discardUpload`, account deletion) deletes every key derived from it at once, and again after its presigned PUT has expired and any processing or publishing run that started before has ended (at least an hour later). So a PUT that lands after a discard, or a run that dies between its writes and its re-check, can't leave an object behind, including an evidence original with its GPS.

## Publishing task photos

A task photo stays in the private bucket until a task claims it (`claim_uploads`, BEAV-85/86/87). The claim queues the Celery task `uploads.publish` once its transaction commits, which copies the clean copy to the public bucket (retried on R2 errors; the `uploads.sweep` Beat task re-queues a claimed photo still unpublished at most once an hour, after the previous retry chain must have ended, and logs a warning each time). A row deleted while its photo is being processed or published can't leave objects behind: the run deletes what it wrote (falling back to the retried `uploads.delete_objects` task). Until then the owner sees the photo through a 5-minute presigned GET, and a task page shows it only once published (`uploads.services.public_photo_url`). So the public bucket can't be used to host files nothing uses.

## API token

One R2 API token per environment with **Object Read & Write** on that environment's two buckets only. Its access key ID and secret are `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY`.

## CORS on the private bucket

Browsers PUT to the private bucket from the web app, so it needs a CORS rule (the mobile app doesn't):

```json
[
  {
    "AllowedOrigins": ["https://taskbeavo.com", "https://www.taskbeavo.com"],
    "AllowedMethods": ["PUT"],
    "AllowedHeaders": ["content-type"],
    "MaxAgeSeconds": 3600
  }
]
```

Staging uses its own web origin (and the Vercel preview origin if previews upload). Add `http://localhost:3000` only to a local or staging bucket, never production.

## Limits the API enforces

- JPEG, PNG or WebP, at most `UPLOAD_MAX_BYTES` (10 MB). The presigned PUT signs the content type and the exact length, so R2 refuses any other file.
- `UPLOAD_MAX_PIXELS` (50 MP) before decoding; the clean copy's longest side is at most `UPLOAD_MAX_DIMENSION_PX` (2560).
- At most `UPLOAD_MAX_PENDING_PER_USER` (20) uploads per user that nothing uses yet (URL issued, being processed, or READY and unclaimed); the owner frees a slot with the `discardUpload` mutation, and `createUploadUrl` is rate-limited (`UPLOAD_URL_RATE_LIMIT`, 20 a minute).
- Uploads no task or booking claims are deleted, objects included, after `UPLOAD_UNATTACHED_RETENTION_HOURS` (48) by the `uploads.sweep` Beat task.
- Evidence photos are refused from web sessions (`EVIDENCE_NEEDS_APP`): they are taken in the app. Their trusted time is `received_at`, when `completeUpload` confirms the object; EXIF time and GPS are kept only as untrusted `exif_taken_at` and `exif_location`.

## Retention

Settings, in `backend/config/settings/base.py`; change them with environment variables, no code change. The owning objects start the clock with `uploads.services.set_retention` and place or lift legal holds; the `uploads.sweep` Beat task deletes expired, unheld rows and every R2 object they may have. How tasks, bookings, no-access reports and disputes call it is in the `backend/uploads/models.py` docstring.

| Upload | Kept | Setting |
|---|---|---|
| Never claimed | 48 hours | `UPLOAD_UNATTACHED_RETENTION_HOURS` |
| Task photo (private clean copy and, while the task is open, its public copy) | Until the task closes or expires, plus 30 days | `UPLOAD_TASK_PHOTO_RETENTION_DAYS` |
| Task photo on a draft that is never published | 30 days after the draft was last saved | `TASK_DRAFT_PHOTO_RETENTION_DAYS` |
| Evidence photo (original, clean copy, EXIF data) | 180 days after the booking closes | `UPLOAD_EVIDENCE_RETENTION_DAYS` |
| Evidence, booking ended in a no-access call-out, partial release or refund | 18 months after payment | `UPLOAD_EVIDENCE_PAYMENT_ISSUE_RETENTION_MONTHS` |
| Linked to an open dispute, chargeback or claim | Legal hold: until resolved, plus 5 years | `UPLOAD_LEGAL_HOLD_RETENTION_YEARS` |

## GPS evidence (BEAV-125)

Device GPS at the door is not captured yet. BEAV-125 adds `expo-location`, the location prompt and the 100 m check against the task address: the app sends its position with `completeUpload` for an `EVIDENCE_PHOTO`, and the server stores it next to `received_at` on the `Upload` row (`backend/uploads/services.py` `complete_upload`). Nothing trusts EXIF GPS.

## Local development

Without the R2 variables, `createUploadUrl` fails; everything else runs. Tests never touch R2: they use the in-memory fake in `backend/uploads/tests/fakes.py`.
